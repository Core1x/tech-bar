# 极客信息聚合站产品优化执行方案

> 状态：已按本方案逐里程碑执行完毕（M0–M5，2026-09-18；各项落地与验证结果回写 `docs/execution-plan.md` §2「产品优化轮」各节与总验收）
> 日期：2026-09-15
> 目标：把现有多源聚合能力组织成一条稳定的“发现 → 判断 → 对比 → 持续跟踪”路径
> 默认产品形态：本地、单用户、桌面优先，同时保证移动端可正常使用

## 1. 文档定位

本文是后续产品优化的执行规格，供开发 agent 按里程碑实现。它不替代现有文档：

- `docs/architecture.md` 继续作为目标技术架构的权威说明。
- `docs/execution-plan.md` 继续记录已完成状态与验证结果。
- `docs/optimization-plan.md` 继续记录既有工程加固项。
- 本文只定义产品目标、交互、数据要求、实施顺序和验收条件。

执行时每个里程碑应单独完成、单独验证、单独回写状态。不得一次性跨多个里程碑大改。

## 2. 产品判断

现有项目已经具备完整的信息采集和分析能力：多源信息流、GitHub 增量榜与存量榜、确定性判读信号、AI 综述、日报、周报、趋势雷达、自然语言寻找、关注和详情页。

当前主要问题是这些能力以独立页面和独立模块存在，用户仍要浏览大量内容并自行拼接判断。首页一天可出现数十条信息；关注只承担当前列表过滤；AI 判读、评测和同类项目存在重复；趋势数据积累后仍以列表为主；部分 AI 缓存会引用已经变化的旧数据。

本轮优化不继续增加信息源数量，先提高以下三项核心价值：

1. 用户每天能更快找到少量真正值得看的内容。
2. 用户能理解推荐依据，并确认 AI 结果基于哪一版数据。
3. 用户关注一个项目后，能持续看到它发生了什么变化。

## 3. 产品原则

### 3.1 确定性数据优先

排序、过滤、许可证、维护状态、star 增量、首次发现时间等结论应由确定性逻辑产生。AI 负责解释、归纳和补充选型建议，不负责伪造确定性指标。

### 3.2 所有 AI 结论必须可判断新鲜度

AI 内容必须显示生成时间、数据时间和状态。数据已更新但内容仍基于旧快照时，界面必须标记“数据已更新，可重新生成”，不得继续只显示“已生成”。

### 3.3 保留原始信息流

优化首页优先级不等于删除原始数据。完整多源信息流继续保留，作为用户下钻和核对的入口。

### 3.4 关注代表长期意图

用户点击关注后，该条目必须能在独立页面再次找到。GitHub 关注项目即使离开今日榜单，也应继续积累最基本的趋势数据。

### 3.5 无 AI Key 时核心功能仍可用

今日推荐、关注中心、趋势图、项目事实和对比矩阵必须有确定性降级。无 AI Key 时只隐藏或降级解释性内容。

### 3.6 保持本地单用户边界

本轮不引入账号、远程数据库、团队协作、消息推送和公网部署能力。若后续决定做公开产品，应另立方案处理鉴权、租户隔离、密钥、限流和服务端任务。

## 4. 目标信息架构

全部里程碑完成后，导航调整为：

| 一级入口 | 内容 | 对应现有能力 |
|---|---|---|
| 今日 | 今日简报、异常变化、完整多源信息流 | 当前首页、跨源综述 |

导航改名在对应页面能力完成后统一执行。里程碑 M0～M2 期间保留当前导航，避免出现空入口。

## 6. M0：可用性与可信度基线

### M0.1 修复移动端布局阻断

#### 当前问题

根布局始终为横向 `flex`。小屏时桌面侧栏隐藏，但移动导航仍作为横向容器中的第一个普通子项，导航自身宽度超过视口并把主内容推到右侧。390px 实测页面文档宽度约 594px，首屏基本看不到主内容。

#### 实现要求

- 根布局在小屏使用纵向结构，在 `md` 及以上切换为横向结构。
- 移动导航占满可视宽度，自身可横向滚动，但不得扩大整个文档宽度。
- 主内容容器必须具备 `min-width: 0` 和正确的宽度约束。
- 右下角聊天、翻译按钮不得遮挡主要按钮和移动导航。
- 不通过全局 `overflow-x: hidden` 掩盖布局错误；必须消除实际溢出来源。

#### 主要涉及文件

- `app/layout.tsx`
- `components/Sidebar.tsx`
- `components/ChatWidget.tsx`
- `components/TranslateWidget.tsx`
- 必要时 `app/globals.css`

#### 验收标准

- 320×568、390×844、768×1024、1280×720 四档下，首页、热榜、寻找、洞察、雷达、设置和仓库详情均可看到主内容。
- 320px 和 390px 下 `document.documentElement.scrollWidth <= clientWidth + 1`。
- 移动导航可访问全部入口，当前入口状态正确。
- 页面不存在被浮动按钮永久遮挡的操作。

### M0.2 为 AI 产物增加来源版本与过期状态

#### 当前问题

- 项目评测缓存只按仓库名保存，内容可能长期不刷新。
- 跨源综述在同一天刷新数据后仍可能复用旧内容。
- 页面只显示“已生成”，用户看不到生成时间和依据的数据时间。
- AI 文本可能引用旧 star 或旧增量，与当前卡片指标冲突。

#### 数据要求

新增统一元数据结构，允许使用主文件内 envelope 或同名 `.meta.json` sidecar。优先选择对现有 Markdown 读取影响最小的实现，但所有新产物必须能得到以下字段：

```ts
interface ArtifactMeta {
  schemaVersion: 1;
  kind: "cross-digest" | "digest" | "weekly" | "verdict" | "review" | "similar" | "decision";
  generatedAt: string;
  sourceDate: string;
  sourceUpdatedAt: string | null;
  sourceFingerprint: string;
  model?: string | null;
}
```

规则：

- `sourceFingerprint` 由实际进入该 AI 请求的数据计算，不能只取当天日期。
- 同一天重新拉取数据后，如果输入已经改变，旧产物状态为 `stale`。
- 旧缓存没有元数据时按 `legacy` 读取，界面显示“历史缓存，依据时间未知”。
- 不批量改写现有 `data/` 运行数据；采用读取兼容和按需升级。
- “重新生成”成功后替换当前有效版本，生成失败时保留旧内容并展示错误。
- 对无需频繁变化的判读，可以排除纯 star 数；如果正文引用了具体 star 或增量，则这些字段必须进入指纹。

#### 界面状态

统一为：

- 未生成
- 生成中
- 已生成 · 基于最新数据
- 数据已更新 · 可重新生成
- 历史缓存 · 依据时间未知
- 生成失败 · 可重试
- 未接入 AI

展开内容时显示“生成于”和“数据更新于”。

#### 首批覆盖范围

- 首页跨源综述
- 项目 AI 判读
- 项目 AI 评测
- 同类项目

日报和周报元数据可以在 M4 补齐，但共享结构必须从 M0 开始复用。

#### 验收标准

- 同一天更新数据后，跨源综述能识别为过期。
- 修改仓库维护、许可或描述输入后，项目判读能识别为过期。
- 旧 `.md` 缓存仍可显示，不导致 500。
- 界面不会同时展示当前指标和未经标记的旧指标结论。
- 无 AI Key、上游失败和旧缓存三种状态有不同文案。

## 7. M1：首页“今日必须看”

### 7.1 目标

用户进入首页后，不浏览完整 59 条信息也能在一分钟内知道今天最值得看的 3～5 条内容以及推荐理由。

### 7.2 页面结构

首页从上到下调整为：

1. 页面标题、数据时间和更新按钮。
2. “今日必须看”简报，默认展开。
3. “异常变化”轻量区域，有数据时显示。
4. “完整信息流”，保留现有来源 Tab、关注过滤和板块。
5. 原“今日跨源值得看”合并进简报解释，不再以独立大段 Markdown 抢占结构。

### 7.3 今日候选与排序

先由确定性算法选择候选，再让 AI 为已选候选写解释。不得让模型从未经约束的全量文本直接决定榜单。

候选信号包括：

- GitHub 当日绝对增量和相对增幅。
- 仓库是否新进入本站视野。
- 同主题是否跨两个以上信息源出现。
- 掘金、博客园等各自源内热度，不进行跨源数值混排。
- 是否与用户关注主题或项目相关，M5 前该项可为空。
- 归档、长期未更新、无许可证等负面信号。

输出最多 5 条，并限制单一来源最多 3 条。每条包含：

- 标题、来源、原生指标。
- 一句“为什么今天值得看”。
- 1～3 个可核实依据。
- 风险标签。
- 打开、关注、加入对比三个操作；非 GitHub 条目不显示加入对比。

AI 不可用时，用规则模板生成理由，例如“今日新增 star 排名第 2，且同主题在掘金出现”。

### 7.4 异常变化

只展示真正需要注意的变化：

- 关注项目明显加速或降温。
- 项目变为归档。
- 许可证从明确变为缺失或发生变化。
- 数据源更新失败或明显过期。

没有变化时不显示空面板。

### 7.5 数据建议

新增面向 UI 的结构化结果，不直接把 AI Markdown 当作整个模块：

```ts
interface TodayBriefing {
  date: string;
  sourceUpdatedAt: string;
  sourceFingerprint: string;
  generatedAt: string;
  items: Array<{
    key: string;
    reason: string;
    evidence: string[];
  }>;
}
```

条目事实继续从 `FeedItem` 读取，缓存只保存选择结果和解释，避免复制后产生指标漂移。

### 7.6 验收标准

- 首屏最多展示 5 条推荐，不默认展开完整 GitHub 20 条。
- 每条推荐可回到原条目或仓库详情。
- 更新数据后简报能显示过期并可重建。
- 无 AI Key 时仍有确定性今日推荐。
- 完整信息流功能和各源原生指标不丢失。

## 8. M2：关注中心与持续跟踪

### 8.1 新入口

新增 `/watch` 页面。完成后侧栏新增“关注”，首页和热榜的“只看关注”仍保留为快捷过滤。

### 8.2 页面内容

顶部显示：

- 关注总数。
- 今日有变化的数量。
- 数据更新时间。

列表支持：

- 全部、GitHub、文章三个类型过滤。
- 最近变化、最近关注、名称排序。
- 当前可获得的原生指标。
- 加入关注时间。
- 最近变化摘要。
- 取消关注。

空状态必须解释如何从首页、热榜或详情页加入关注，并提供返回入口。

### 8.3 GitHub 持续采样

- 每日 GitHub 更新的追踪集合调整为“固定 tracked repos ∪ watchlist 中的 GitHub 仓库”。
- 取消关注时不得删除用户手工配置在 `tracked-repos.json` 中的仓库。
- 关注新仓库后无需等第二天即可在关注页出现；趋势数据从下一次更新开始积累。
- API 配额不足时保留 last-known 数据并标记更新时间，不把旧数据显示成刚更新。

### 8.4 非 GitHub 条目

- 文章离开今日快照后，关注页仍保留标题、来源、URL、关注时间和最后一次已知指标。
- 不要求第一版持续抓取文章指标。
- 原文失效时保留记录并显示最后已知状态。

### 8.5 数据兼容

可扩展现有 `WatchlistEntry`，不得破坏只有 `source/source_id/addedAt` 的旧记录：

```ts
interface WatchlistEntry {
  source: string;
  source_id: string;
  addedAt: string;
  note?: string;
  snapshot?: {
    title: string;
    url: string;
    description?: string | null;
    lastMetricLabel?: string | null;
    capturedAt: string;
  };
}
```

### 8.6 验收标准

- 关注条目第二天离开榜单后仍能从 `/watch` 找到。
- GitHub 关注仓库会进入后续历史采样。
- 取消关注不会误删固定追踪仓库。
- 空关注、旧记录、原文失效和配额不足均有明确状态。
- 首页、热榜和关注页的关注状态保持一致。

## 9. M3：项目决策卡与对比

### 9.1 合并详情页 AI 模块

将“AI 判读”和“AI 评测”在界面上合并为“项目决策”。旧接口可暂时保留兼容，但页面不再让用户理解两者差异。

决策卡结构固定为：

1. 结论：推荐尝试、继续观察、谨慎投入、仅供参考。
2. 适合场景。
3. 不适合场景。
4. 为什么现在值得看。
5. 确定性事实。
6. 风险。
7. 尚无法判断。
8. 生成时间、数据时间和重新生成。

### 9.2 输入事实

优先使用 GitHub 单次仓库详情可以获得的字段，避免无上限增加 API 请求：

- star、fork、open issues、创建时间、最后推送。
- archived、license、language、topics、homepage。
- 当日增量和本站历史趋势。
- README 哈希和受长度限制的关键片段。
- 最新 release 作为可选的一次补充请求；失败时降级，不阻塞决策卡。

不得根据 star 高直接推导“代码质量高”或“社区支持好”。没有 issue 响应时间、贡献者等数据时放入“尚无法判断”。

### 9.3 详情页事实区

顶部事实从目前的四项扩展为：

- 总 star。
- 当日或近日增量，并标明时间口径。
- fork。
- open issues。
- 语言。
- 许可证。
- 最后推送。
- 创建时间。

趋势样本少于 3 天时显示“样本不足，暂不能判断趋势”，仍允许展示数据点。

### 9.4 对比入口

新增 `/compare` 页面和全局本地对比篮，最多 4 个 GitHub 仓库。以下位置可加入：

- 今日简报。
- GitHub 热榜。
- AI 寻找结果。
- 仓库详情。
- 同类项目。

对比篮使用 `localStorage` 即可，不进入账号或服务端同步范围。

### 9.5 对比矩阵

第一版字段：

- 项目定位。
- star 与近 7 日增长。
- fork。
- 最后推送。
- 许可证。
- 主要语言。
- 创建时间。
- 最新 release。
- 归档和维护风险。
- README 中明确提供的部署方式或运行环境。

事实矩阵无 AI 也可用。用户输入一句使用场景后，AI 可以在矩阵下生成“按该场景如何选择”，必须引用矩阵字段。

### 9.6 同类项目质量门槛

- 返回 3～4 个真正解决相同需求的候选；不足时明确显示不足，不用低质量仓库凑数。
- 候选需要同时考虑主题重叠、描述语义、维护状态和基础流行度。
- 默认排除归档仓库。
- 0 star 或信息严重缺失的项目默认不进入推荐，除非能明确说明特殊相关性。
- 每个候选直接提供“加入对比”。

### 9.7 验收标准

- 页面只出现一个统一项目决策入口。
- 决策内容能区分事实、判断和未知项。
- 当前数据变化后决策卡能识别过期。
- 用户可以从至少四个入口加入对比。
- 2～4 个项目可以形成无 AI 可用的事实矩阵。
- 同类项目不再用明显无效候选填满数量。

## 10. M4：趋势与报告行动化

### 10.1 趋势雷达

在现有列表上增加轻量 SVG 可视化，不为此引入大型图表依赖：

- 近 7 日增长 Top 的迷你折线。
- 绝对增长与相对增长切换。
- 选中 2～5 个仓库叠加比较。
- 主题热度近几周变化。
- 增速放缓项显示前后两个时间段的趋势，而不只显示 ratio。

“本周新入视野”统一改为“本周首次被本站发现”，避免被理解为仓库刚创建。

### 10.2 每日洞察

AI 正文可以继续以 Markdown 存储，但渲染时为识别出的 GitHub 仓库补内部链接，并在“值得关注的项目”区域提供关注和加入对比操作。

每篇洞察显示：

- 生成时间。
- 数据覆盖时间。
- 使用的信息源。
- 是否基于当前最新快照。

### 10.3 验收标准

- 用户能直观看到增长曲线和增速变化。
- 绝对增量和百分比增量不会混为一个排名口径。
- 日报中的仓库可以直接进入详情、关注或对比。
- 历史日报和周报仍能正常读取。

## 11. M5：寻找、数据源和兴趣偏好

### 11.1 AI 智能寻找

首次进入页面增加可点击的示例需求，不保留大面积无内容区域。建议示例：

- 本地部署大模型。
- React 数据可视化。
- 自托管团队知识库。
- PDF 转 Markdown。
- Rust 桌面应用。

增加筛选：

- 语言。
- 最低 star。
- 最近更新时间。
- 许可证明确与否。
- 是否归档。

把现有“非开源”改为“无明确许可证”。公开仓库没有许可证不应被描述为私有项目。

结果卡增加：

- “为什么匹配”的字段级解释。
- 最后推送与许可证。
- 关注和加入对比。
- 搜索条件摘要和一键清除。

### 11.2 数据源管理

在设置页增加：

- 当前启用的数据源。
- 每个源最后成功更新时间。
- 最近一次更新状态。
- 启用和停用开关。
- HN 等外网源的网络要求说明。

界面修改继续写入现有 `active-sources.json`，不另建重复配置。

### 11.3 兴趣偏好

新增本地偏好配置：

- 关注语言。
- 关注主题。
- 不感兴趣主题。
- 首页更偏向“新项目”或“成熟项目”。

偏好只影响“今日必须看”的候选加权，不改变原始榜单和完整信息流。

### 11.4 验收标准

- 首次进入寻找页可以点击示例直接搜索。
- 筛选条件可见、可清除、刷新后按既定策略保留。
- 无许可证仓库文案准确。
- 数据源无需编辑 JSON 即可启停。
- 兴趣偏好只改变简报，不改变原始源数据。

## 12. 横向体验规范

### 12.1 状态文案

全站统一使用以下时间语义：

- “数据更新于”：原始数据抓取时间。
- “生成于”：AI 内容生成时间。
- “今日新增”：明确为自然日口径。
- “近 7 日增长”：明确起止日期。
- “首次被本站发现”：不得简写为“新项目”。

### 12.2 颜色

- 正向增长统一使用绿色或主色，不使用易被理解为风险的红色。
- 风险、失败和过期分别使用不同状态，不把“数据已过期”显示成错误。
- 来源颜色、语言颜色和状态颜色不得共用相互冲突的含义。

### 12.3 空状态

任何空状态都要回答两件事：为什么为空、用户下一步能做什么。重点覆盖关注、对比、寻找、报告和无数据首页。

### 12.4 浮动 AI 工具

- 聊天应接收当前页面上下文，例如当前仓库、当前对比集合或当前雷达筛选。
- AI 回答中的仓库名优先提供内部详情链接。
- 聊天历史刷新清空可以保留为第一版行为，但界面需说明。
- 翻译在仓库 README 页有明确价值；其他页面可收进更多菜单，减少两个浮动按钮长期遮挡内容。

## 13. 数据迁移与兼容要求

- `data/` 继续不入 Git。
- 所有新增字段均为可选，旧快照和旧配置必须可以读取。
- 不执行批量删除缓存。
- 新缓存格式需要提供 legacy 读取分支；用户重新生成后自然升级。
- CLI 与 Web 必须读取同一套核心类型和配置。
- 修改 `core/` 或 `cli/` 后必须重新执行 `npm run build:cli`。
- watchlist、features、active-sources 的写入继续使用原子写和串行化策略。

## 14. 验证要求

每个里程碑至少执行：

```bash
npm test
npm run lint
npm run build
```

涉及 `core/` 或 `cli/` 时额外执行：

```bash
npm run build:cli
```

需要真实页面走查的场景：

- 有 AI Key 与无 AI Key。
- 有数据、无数据、旧数据和部分源失败。
- 空关注与有关注。
- 对比 0、1、2、4 个项目。
- 320px、390px、768px、1280px 四档视口。
- 数据更新前后 AI 产物状态变化。

不得把运行期 `data/` 变化提交进 Git。

## 15. 建议产品指标

本地产品也可以记录匿名本地事件计数，不需要上传：

| 指标 | 定义 | 用途 |
|---|---|---|
| 简报行动率 | 今日推荐中发生打开、关注或对比的条目数 / 曝光条目数 | 判断推荐是否有用 |
| 首次有效操作时间 | 打开首页到第一次打开、关注或对比 | 判断是否降低信息负担 |
| 关注次周回访率 | 本周关注后，下周再次打开关注页的比例 | 判断持续跟踪价值 |
| AI 新鲜度异常率 | 页面检测到 AI 产物与当前输入指纹不一致的次数 | 判断可信度 |
| 对比完成率 | 创建两个以上候选后查看完整对比的比例 | 判断选型闭环 |

事件仅落本地汇总，不记录聊天正文、搜索原文、API Key 或完整浏览历史。

## 16. 本轮明确不做

- 不增加新的内容源。
- 不做账号和多用户体系。
- 不做云同步、邮件、微信或系统通知。
- 不做在线支付或商业化。
- 不引入数据库。
- 不让 AI 直接修改用户关注、配置或追踪池。
- 不重写现有采集架构。
- 不为了视觉效果引入大型 UI 或图表框架。

## 17. 审阅决策点

执行前需要产品负责人确认以下方向，未特别修改时采用括号内默认值：

1. 产品继续以本地单用户为主，还是准备公开部署。（默认：本地单用户）
2. 是否接受最终导航调整为“今日 / 发现 / 关注 / 对比 / 报告”。（默认：接受）
3. 是否接受把“AI 判读”和“AI 评测”合并为一个“项目决策”。（默认：接受）
4. 首页“今日必须看”最多展示几条。（默认：5 条）
5. 是否允许关注的 GitHub 仓库自动进入每日追踪集合。（默认：允许）
6. 是否先执行 M0，验收后再依次执行后续里程碑。（默认：是）
